hippobridge — internal note

What a Hipocrate cerere status actually means

A field-verified map of every request/exam status hippobridge has observed live, what (NV) / (PV) most likely stand for, and where the "performed but not yet reported" gap sits — with a draft ask for the Hipocrate team.

1. The eleven statuses, confirmed live

Pulled from /PARA/NOM/Listare/?id=44 (the schedule/worklist listing) across a live query of 1,018 requests, 2026‑01‑01 → 2026‑08‑09. This is the complete set actually seen — anything not in this table hasn't shown up in nine months of requests, though that isn't proof it can't exist (see §4).

2. What NV / PV most likely stand for

Hipocrate never spells the abbreviation out anywhere in the page markup or JS we could reach (no tooltip, no legend). But cerere.asp exposes a per-request change log at ajax_modificari.asp?Id=… with two distinct sections — MODIFICARI / INTRODUCERI REZULTATE (who typed a result, and when) and VALIDARI REZULTATE (who signed it off, and when) — and comparing that log against the request's item count across live examples pins the abbreviation down behaviorally, even without Hipocrate's own definition.

cerere 1715945 — ES9634 — status: In lucru(PV) — 2 items requested
Cerere introdusa de: FLORIN CRISTIAN DRAGOMIR — 11 Jun 2026 07:50

MODIFICARI / INTRODUCERI REZULTATE:
  IMAGISTICA PRIN REZONANTA MAGNETICA A CREIERULUI — ADRIAN DR. MARGARIT — 26 Jun 2026 10:35

VALIDARI REZULTATE:
  (empty — nothing validated)
cerere 1742674 — status: Cerere completata — 2 items requested
MODIFICARI / INTRODUCERI REZULTATE:
  Anestezia generala, ASA 29 — Silviu Florin Mihaila — 07 Aug 2026 09:25
  IMAGISTICA PRIN REZONANTA MAGNETICA A CAPULUI — Rezident Garda Radiologie — 07 Aug 2026 12:23

VALIDARI REZULTATE:
  (empty — nothing validated)

Pattern: 1715945 has a result for 1 of its 2 items → PV. 1742674 has results for 2 of its 2 items → the status graduates from "in lucru" to Cerere completata outright. Neither has any validation logged, yet neither uses a validation-flavored label — so V in NV/PV reads as results entered, not validated:

  • NV — Nici un rezultat V(izat/introdus): zero items reported yet.
  • PV — Parțial V(izat/introdus): some but not all items reported.
Confidence: inferred, not confirmed
This is the reading that fits every example we could pull live, but hippobridge never saw a live NV case to test the zero-items-reported half of the hypothesis, and Hipocrate's own glossary (if one exists) hasn't been checked. Worth a direct question in §5 rather than treating this as settled.

3. The journey, as actually observed

stateDiagram-v2
    [*] --> netrimisa: request created
    netrimisa: Cerere netrimisa
    trimisa: Trimisa in laborator
    primita: Primita in laborator
    lucru_nv: In lucru (NV)\n0 / N items reported
    lucru_pv: In lucru (PV)\n1..N-1 / N items reported
    completata: Cerere completata\nN / N reported, 0 validated
    completata_pv: Cerere completata\n/ partial validata
    terminata: Terminata(!)\nN / N reported AND validated
    anulata: Cerere anulata
    fara: Fara analize

    netrimisa --> trimisa: sent to lab
    trimisa --> primita: lab receipt
    primita --> lucru_nv: work begins
    lucru_nv --> lucru_pv: first result entered
    lucru_pv --> lucru_pv: more results entered
    lucru_pv --> completata: last item reported
    completata --> completata_pv: first validation
    completata_pv --> terminata: last validation
    completata --> terminata: all validated at once

    netrimisa --> anulata: cancelled
    trimisa --> anulata: cancelled
    primita --> anulata: cancelled
    lucru_nv --> anulata: cancelled
    lucru_pv --> anulata: cancelled

    netrimisa --> fara: no analyses attached

Dotted through-line: reporting (someone types findings) and validation (someone signs off) are tracked as two separate events per item — the status text only ever encodes the reporting side (NV/PV/completata) or the fully-validated end state (terminata). There is no status in between that says "reported, awaiting sign-off" for a single-item request — see §4.

4. The actual gap: "performed" isn't tracked at all

Everything in §1–3 is downstream of a report being typed. Nothing in this vocabulary reflects that the exam happened — a technologist ran the scanner, at a known time, and no radiologist has looked at it yet. Two things confirm the field for that doesn't work the way it should:

  • DataEfectuarii ("Data Efectuarii" / exam-performed date) is manual and decoupled from acquisition. It's a plain form field on cerere.asp, set only when someone calls the "Perform" action (hdnAction=S) — usually the person entering the report. On live request 1715945 above, a radiologist had already typed MRI findings, yet Data Efectuarii was still blank ("-" in the schedule listing). The field that's supposed to mean "this happened" doesn't get set even after it demonstrably did.
  • No field records who ran the study. The change log has RECOLTAT DE / RECEPTIONAT DE (specimen collected/received by — lab workflow only) and result-entry attribution (the radiologist who typed findings). There's no equivalent for imaging's technologist/operator.

hippobridge already has the right raw signal for this: DICOM MPPS (ModalityPerformedProcedureStep, added to worklist.py's SCP on 2026‑08‑07, currently observation-only) carries exactly performed date/time and operator name straight from the modality, independent of any human touching Hipocrate afterward. As of this note it has logged zero MPPS messages — no connected modality is sending it yet — so it's unverified in practice, but it's the mechanism that would close this gap once wired up.

4.1 "Performed" existed before the Hipocrate upgrade — and got lost

The code as it stood right before Hipocrate's 2026‑06‑09 upgrade (commit 7c099a2, "fix: adapt all scrapers to Hipocrate server URL and HTML changes" — the one where every scraper broke at once) was checked out directly for comparison.

The cerere.asp status vocabulary (§1–3) didn't exist at all before that commit. HipoClientCerere and HipoClientSchedule weren't in the codebase — they were added after the rewrite, adapting to the new Hipocrate. There's no older vocabulary to compare against; the one above is entirely new.

But "performed by someone" existed explicitly, and it's now dead code. The old HipoClientDiagnosticReport (reading the printed bulletin at /analyse/Reports/analyseFile.asp) had a direct label on the page:

hipoclient.py, pre-upgrade (parent of commit 7c099a2)
# Extract performer (Efectuata de catre:)
data.store("study.performer", extract_text_after_label(soup, r'Efectuata de catre:'))
data.store("study.medic", extract_text_after_label(soup, r'MEDIC,|Medic validator:', ...))

"Efectuata de catre:" = "Performed by:" — an explicit field on the old bulletin naming the person who ran the exam, distinct from the validating physician. That's exactly the operator field this investigation started by asking about.

The June 2026 rewrite moved parsing to BuletinAnalize.asp, which carries no such label (confirmed live — the current ?type=1 and ?type=3 pages for a finished radiology bulletin were checked directly; no "Efectuat"/"performer"/"operator"/"tehnician" text anywhere). Nobody removed the code that consumed that field, though — until this note, hippoclient.py still had:

hippoclient.py, HippoClientDiagnosticReport.fhir_response — before the fix below
performer = parsed_data.get("study.performer")   # never populated since June 2026
if performer:
    fhir_report["performer"] = [...]
medic = parsed_data.get("study.medic")            # same
if medic:
    fhir_report["resultsInterpreter"] = [...]

DiagnosticReport.performer and .resultsInterpreter have therefore been silently empty in every FHIR response since the upgrade — not because Hipocrate stopped tracking who performed or validated a study, but because the label moved pages and nothing followed it. (Per-study validation info does still reach FHIR, through presentedForm[].validator/validation_date, sourced from the current Validat de: label — only "who physically performed the exam" is uncovered.)

Fix applied: the dead code (study.performer/study.medic plus their reads in fhir_response) has been removed from hippoclient.py — there was nothing to restore it from, since "Efectuata de catre:" has no equivalent on any page hippobridge currently reads. This stays a solid argument for the request below: Hipocrate did surface this before, on its own UI — it isn't a new ask, just one lost in migration.

5. Draft request to the Hipocrate dev team

To Hipocrate development team
From hippobridge / radiology integration
Re A status for "performed, awaiting report", and confirming NV/PV

We're integrating DICOM MPPS so hippobridge learns the moment a modality finishes an exam — exact timestamp plus the operator who ran it — independent of anyone touching Hipocrate. Right now there's nowhere for that information to land:

  1. Please confirm what (NV) and (PV) stand for on the "In lucru" status, and whether our reading is right: NV = no items reported yet, PV = some but not all items reported (see evidence above). If there's an internal glossary for the full cerere status vocabulary, that would save us re-deriving it from behavior.
  2. Are there status values we haven't seen? We've only observed the 11 texts above across ~1,000 live requests over 9 months (e.g. never a "no-show" or "rescheduled" case, if those exist as distinct states rather than being handled another way).
  3. A distinct status for "exam performed, no report yet" — something like Efectuat, neexaminat — separate from In lucru(NV), which today is indistinguishable from "not started." This is the state an exam sits in for however long a radiologist takes to pick it up, and right now it's invisible.
  4. A way to set Data Efectuarii (and, ideally, an operator/technologist field) independent of entering a report — an API call or a POST hippobridge can make when MPPS confirms completion, rather than that field only ever being set as a side effect of someone typing findings.
  5. This isn't a new ask — the old bulletin page (before the June 2026 update) had an explicit "Efectuata de catre:" label naming who ran the exam, distinct from the validating physician. It was lost in the move to BuletinAnalize.asp and has no equivalent today on any page we read. We'd simply like that information back, in whatever form it's available now.

Happy to share the raw MPPS payloads once a modality actually sends us one, if that helps scope this.
